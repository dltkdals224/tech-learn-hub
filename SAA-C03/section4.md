## 1. IAM 개요

**IAM(Identity and Access Management)** 은 AWS 리소스에 대한 접근을 제어하는 서비스다.

- **글로벌 서비스**: 특정 리전에 종속되지 않으며 모든 AWS 리전에서 동일하게 적용된다
- AWS 계정을 처음 만들면 **Root 계정**이 생성된다

**Root 계정 vs 일반 사용자**

| 구분      | Root 계정                          | 일반 사용자(IAM User)        |
| --------- | ---------------------------------- | ---------------------------- |
| 권한      | 모든 AWS 서비스에 대한 무제한 권한 | 정책(Policy)으로 제한된 권한 |
| 용도      | 계정 초기 설정 시에만 사용         | 일상적인 AWS 작업            |
| 공유 여부 | 절대 공유 금지                     | 개인별 계정 사용             |

> 💡 **시험 포인트**: Root 계정은 AWS 계정 설정 외에는 사용하지 말아야 하며, 절대 다른 사람과 공유해서는 안 됩니다.

## 2. 사용자(User) & 그룹(Group)

### 사용자(User)

- 조직 내 **개인**을 나타내는 IAM 엔티티
- AWS Console 접근을 위한 비밀번호를 가질 수 있다
- 그룹에 반드시 속할 필요는 없다
- **여러 그룹에 동시에 속할 수 있다**

### 그룹(Group)

- **사용자만 포함** 가능하다 (그룹 안에 그룹을 넣는 것은 불가)
- 공통 권한을 가진 사용자들을 묶어서 관리할 때 사용한다
- 그룹에 정책을 연결하면, 그룹 내 모든 사용자가 해당 권한을 상속받는다

**예시 구조:**

```
조직
├── 개발팀 그룹 (EC2, RDS 접근 권한)
│   ├── Alice (개발팀 + 감사팀 동시 소속)
│   └── Bob
├── 감사팀 그룹 (CloudTrail 읽기 권한)
│   ├── Alice
│   └── Charlie
└── Dave (어떤 그룹에도 속하지 않음 - 가능하지만 권장하지 않음)
```

> 💡 **시험 포인트**:
>
> - 그룹에는 사용자만 포함할 수 있으며, **그룹 안에 그룹을 넣을 수 없습니다**
> - 사용자는 여러 그룹에 동시에 속할 수 있습니다
> - 사용자가 그룹에 속하지 않아도 되지만, 권한 관리 측면에서 그룹 사용을 권장합니다

### 최소 권한 원칙 (Least Privilege Principle)

AWS에서 권한을 부여할 때는 **"필요한 최소한의 권한만"** 부여해야 한다.

- 사용자가 필요한 것보다 더 많은 권한을 주지 않는다
- 이는 보안 침해 시 피해를 최소화하기 위한 기본 원칙이다

## 3. IAM 정책(Policies)

**정책(Policy)** 은 사용자 또는 그룹에 부여할 권한을 정의하는 **JSON 문서**다.

### 정책 상속 구조

```
그룹 정책 → 그룹에 속한 모든 사용자에게 적용
인라인 정책 → 특정 사용자에게 직접 연결
```

사용자가 여러 그룹에 속해있다면, 각 그룹의 정책이 **모두 합산**되어 적용된다.

### 정책 JSON 구조

```json
{
  "Version": "2012-10-17",
  "Id": "S3-Account-Permissions",
  "Statement": [
    {
      "Sid": "1",
      "Effect": "Allow",
      "Principal": {
        "AWS": ["arn:aws:iam::123456789012:root"]
      },
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": ["arn:aws:s3:::my-bucket/*"]
    }
  ]
}
```

**각 필드 설명:**

| 필드        | 필수 여부   | 설명                                     |
| ----------- | ----------- | ---------------------------------------- |
| `Version`   | 권장        | 정책 언어 버전. 항상 `"2012-10-17"` 사용 |
| `Id`        | 선택        | 정책의 식별자                            |
| `Statement` | 필수        | 하나 이상의 권한 명세 배열               |
| `Sid`       | 선택        | Statement의 식별자                       |
| `Effect`    | 필수        | `"Allow"` 또는 `"Deny"`                  |
| `Principal` | 상황에 따라 | 정책이 적용될 계정/사용자/역할           |
| `Action`    | 필수        | 허용하거나 거부할 API 액션 목록          |
| `Resource`  | 필수        | 액션이 적용될 AWS 리소스 ARN             |
| `Condition` | 선택        | 정책이 적용될 조건                       |

**Action 예시:**

- `"s3:GetObject"` → S3에서 객체 읽기
- `"ec2:Describe*"` → EC2 관련 모든 Describe 액션 (와일드카드 사용 가능)
- `"*"` → 모든 액션 (주의해서 사용)

> 💡 **시험 포인트**:
>
> - `Effect: "Deny"`는 `Effect: "Allow"`보다 **항상 우선 적용**됩니다 (명시적 Deny > Allow)
> - `Version`은 반드시 `"2012-10-17"`을 사용해야 정책 조건 등 최신 기능이 동작합니다
> - `Principal`은 리소스 기반 정책(Resource-based policy)에서 주로 사용하며, IAM 사용자 정책에서는 생략합니다

## 4. IAM 비밀번호 정책

AWS에서는 IAM 사용자들이 사용할 비밀번호 정책을 계정 수준에서 설정할 수 있다.

**설정 가능한 항목:**

- **최소 비밀번호 길이** 설정
- **특정 문자 유형 요구:**
  - 대문자 포함
  - 소문자 포함
  - 숫자 포함
  - 특수문자 포함
- IAM 사용자가 **스스로 비밀번호를 변경**할 수 있도록 허용
- **비밀번호 만료 기간** 설정 (일정 기간 후 변경 강제)
- **이전 비밀번호 재사용 방지**

> 💡 **시험 포인트**: 강력한 비밀번호 정책은 계정 보안을 높이는 가장 기본적인 방법입니다. 비밀번호 만료 설정과 재사용 방지는 특히 컴플라이언스 요구사항에서 자주 언급됩니다.

## 5. MFA (다중 인증)

**MFA(Multi-Factor Authentication)** 는 비밀번호 + 별도 인증 수단을 결합하여 보안을 강화하는 방식이다.

```
MFA = 알고 있는 것(비밀번호) + 소유한 것(보안 디바이스)
```

**MFA가 중요한 이유:**

- 비밀번호가 유출되더라도 MFA 디바이스가 없으면 계정에 접근할 수 없다
- Root 계정과 권한이 높은 IAM 사용자에게 특히 중요하다

### MFA 디바이스 종류

**① 가상 MFA 디바이스 (앱 기반)**

| 도구                 | 특징                                                |
| -------------------- | --------------------------------------------------- |
| Google Authenticator | 스마트폰 전용                                       |
| Authy                | 스마트폰 전용, **하나의 디바이스에 여러 토큰** 지원 |

**② 하드웨어 U2F 보안 키**

| 도구                  | 특징                                           |
| --------------------- | ---------------------------------------------- |
| YubiKey (Yubico 제조) | **하나의 키로 여러 Root/IAM 사용자 계정** 지원 |

**③ 하드웨어 Key Fob MFA 디바이스**

| 도구            | 용도                       |
| --------------- | -------------------------- |
| Gemalto 제조    | 일반 AWS 계정용            |
| SurePassID 제조 | **AWS GovCloud (US) 전용** |

> 💡 **시험 포인트**:
>
> - Root 계정에는 반드시 MFA를 활성화해야 합니다
> - Authy는 단일 디바이스에서 **여러 토큰**을 관리할 수 있다는 점이 Google Authenticator와의 차이입니다
> - GovCloud 환경에서는 SurePassID Key Fob을 사용합니다

## 6. AWS 접근 방법 3가지

AWS를 사용하는 방법은 크게 세 가지가 있으며, 각각 다른 인증 수단을 사용한다.

| 접근 방법                  | 인증 수단      | 특징                                 |
| -------------------------- | -------------- | ------------------------------------ |
| **AWS Management Console** | 비밀번호 + MFA | 웹 브라우저 기반 GUI                 |
| **AWS CLI**                | Access Key     | 터미널에서 명령어로 제어             |
| **AWS SDK**                | Access Key     | 코드 내에서 프로그래밍 방식으로 제어 |

### Access Key

- AWS Console에서 생성한다
- 사용자가 **직접 자신의 Access Key를 관리**한다
- Access Key는 **절대 공유하면 안 된다** (비밀번호와 동일하게 취급)

```
Access Key ID     = 사용자명(username)과 유사한 공개 식별자
Secret Access Key = 비밀번호와 유사한 비밀 값 (생성 시에만 확인 가능)
```

> 💡 **시험 포인트**:
>
> - Access Key는 생성 직후에만 Secret Access Key를 볼 수 있습니다. 분실 시 재생성해야 합니다
> - Access Key를 코드에 하드코딩하거나 공유 저장소에 올리지 마세요
> - EC2 인스턴스에서 AWS API를 호출할 때는 Access Key 대신 **IAM Role**을 사용해야 합니다

## 7. AWS CLI

**AWS CLI(Command Line Interface)** 는 터미널에서 명령어를 통해 AWS 서비스를 제어할 수 있는 도구다.

**특징:**

- AWS 서비스의 공개 API에 직접 접근
- 반복 작업을 스크립트로 자동화 가능
- 오픈소스 프로젝트 (GitHub에서 소스 확인 가능)
- AWS Management Console의 대안

**기본 사용 패턴:**

```bash
aws <서비스명> <명령어> [옵션]

# 예시
aws s3 ls                          # S3 버킷 목록 조회
aws ec2 describe-instances         # EC2 인스턴스 목록 조회
aws iam list-users                 # IAM 사용자 목록 조회
```

### AWS CloudShell

브라우저 내에서 바로 사용할 수 있는 **클라우드 기반 터미널**이다.

- 별도 CLI 설치 불필요
- AWS 자격증명이 자동으로 구성됨
- 파일 업로드/다운로드 가능
- 일부 AWS 리전에서만 지원됨

> 💡 **시험 포인트**: CloudShell은 브라우저에서 직접 실행되며, 현재 로그인한 IAM 사용자의 권한으로 동작합니다.

## 8. AWS SDK

**AWS SDK(Software Development Kit)** 는 프로그래밍 언어별 라이브러리를 통해 AWS 서비스를 코드에서 직접 사용할 수 있게 해주는 도구다.

**지원 언어:**

- JavaScript, Python, PHP, .NET, Ruby, Java, Go, Node.js, C++
- 모바일: Android, iOS
- IoT 디바이스: Embedded C, Arduino

**특징:**

- 애플리케이션 코드 내에 포함되어 동작
- Access Key로 인증
- AWS 서비스를 애플리케이션 로직에서 직접 호출 가능

**예시 (Python - boto3):**

```python
import boto3

s3 = boto3.client('s3')
response = s3.list_buckets()
print(response['Buckets'])
```

> 💡 **시험 포인트**: **AWS CLI 자체가 Python SDK(boto3)를 기반으로 만들어졌습니다.** SDK를 지정하지 않으면 기본값으로 사용되는 SDK는 Python입니다.

## 9. IAM 역할(Roles)

**IAM Role** 은 AWS 서비스가 다른 AWS 서비스에 접근할 때 사용하는 권한 엔티티다.

### Role이 필요한 이유

EC2 인스턴스가 S3에서 파일을 읽어야 한다고 가정해보자.

- ❌ 잘못된 방법: EC2 인스턴스에 Access Key를 직접 저장
  - 보안 위험: 인스턴스가 해킹되면 키가 노출됨
  - 관리 부담: 키 교체 시 모든 인스턴스를 수동으로 업데이트해야 함

- ✅ 올바른 방법: EC2 인스턴스에 **IAM Role**을 연결
  - AWS가 임시 자격증명을 자동으로 관리
  - 키 노출 위험 없음

### 자주 사용되는 Role 종류

| Role 유형                | 설명                                       |
| ------------------------ | ------------------------------------------ |
| **EC2 Instance Role**    | EC2 인스턴스가 다른 AWS 서비스에 접근할 때 |
| **Lambda Function Role** | Lambda 함수가 AWS 서비스를 호출할 때       |
| **CloudFormation Role**  | CloudFormation이 리소스를 생성/수정할 때   |

> 💡 **시험 포인트**:
>
> - EC2 인스턴스에서 AWS API를 호출해야 할 때는 항상 **IAM Role**을 사용하세요. Access Key를 인스턴스에 저장하는 것은 보안 위반입니다
> - Role은 영구적인 자격증명이 아닌 **임시 자격증명(STS 토큰)** 을 제공합니다

## 10. IAM 보안 도구

IAM에는 계정 내 권한 현황을 감사(Audit)하기 위한 두 가지 도구가 있다.

### IAM Credentials Report (자격증명 보고서)

- **범위**: 계정 전체(Account-level)
- **내용**: 계정 내 모든 IAM 사용자와 각 사용자의 자격증명 상태
  - 비밀번호 마지막 사용일
  - Access Key 활성화 여부 및 마지막 사용일
  - MFA 활성화 여부
- **용도**: 보안 감사, 미사용 계정/키 식별

### IAM Access Advisor (액세스 어드바이저)

- **범위**: 사용자 단위(User-level)
- **내용**: 특정 사용자에게 부여된 서비스 권한과 **마지막으로 해당 서비스를 사용한 날짜**
- **용도**: 실제로 사용하지 않는 권한을 찾아내어 최소 권한 원칙에 맞게 정책을 수정

> 💡 **시험 포인트**:
>
> - **Credentials Report** = 계정 전체 사용자의 자격증명 상태 전체 보고서
> - **Access Advisor** = 특정 사용자의 서비스별 마지막 접근 시간 (권한 최적화용)
> - 두 도구 모두 최소 권한 원칙 실천을 위한 감사 목적으로 사용합니다

## 11. IAM 모범 사례 & 요약

### 모범 사례 (Best Practices)

- **Root 계정**은 AWS 계정 초기 설정 외에는 사용하지 않는다
- 한 명의 실제 사람 = 하나의 IAM 사용자 계정 (계정 공유 금지)
- 사용자를 그룹에 포함시키고, **그룹에 권한(정책)을 부여**하여 관리한다
- 강력한 **비밀번호 정책**을 설정한다
- **MFA 사용을 강제**한다 (특히 Root 계정과 권한이 높은 계정)
- AWS 서비스에 권한을 부여할 때는 **IAM Role**을 사용한다
- 프로그래밍 방식 접근(CLI/SDK)에는 **Access Key**를 사용한다
- **IAM Credentials Report**와 **IAM Access Advisor**로 정기적으로 권한을 감사한다
- IAM 사용자와 Access Key는 절대 **공유하지 않는다**

### 전체 구성요소 요약

| 구성요소        | 설명                                          |
| --------------- | --------------------------------------------- |
| **Users**       | 실제 사람에 매핑, AWS Console용 비밀번호 보유 |
| **Groups**      | 사용자만 포함 (그룹 중첩 불가)                |
| **Policies**    | 사용자/그룹의 권한을 정의하는 JSON 문서       |
| **Roles**       | EC2 등 AWS 서비스에 부여하는 권한             |
| **Security**    | MFA + 비밀번호 정책으로 보안 강화             |
| **AWS CLI**     | 커맨드라인에서 AWS 서비스 제어                |
| **AWS SDK**     | 프로그래밍 언어로 AWS 서비스 제어             |
| **Access Keys** | CLI/SDK 사용 시 필요한 자격증명               |
| **Audit**       | IAM Credentials Report + IAM Access Advisor   |
