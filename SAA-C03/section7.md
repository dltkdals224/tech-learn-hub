## 1. EBS Volume

**EBS(Elastic Block Store) Volume**은 EC2 인스턴스에 연결할 수 있는 네트워크 드라이브.  
인스턴스가 종료된 후에도 데이터를 유지할 수 있으며, (물리적 실체는 없지만)"네트워크 USB"에 비유할 수 있다.

**주요 특징:**

- 네트워크를 통해 인스턴스에 연결 (물리적 연결이 아님 → 약간의 지연 발생 가능)
- 특정 AZ에 종속됨 (us-east-1a의 EBS는 us-east-1b에 직접 연결 불가)  
   ⚠️ 바로 뒤에 언급하는 EBS snapshots를 통해 다른 가용 영역으로 옮길 수 있음
- 프로비저닝(사전 정의)된 용량(GB, IOPS)에 대해 비용 청구
- 한 번에 하나의 인스턴스에만 연결 가능 (io1, io2에서의 Multi-Attach 예외)  
   ⚠️ 동시 쓰기를 제어할 수 있는 클러스터형 애플리케이션용으로 multi-attach를 지원한다. (조건은 아래와 같음)
  - io1 또는 io2 타입만 가능
  - Nitro 기반 EC2만 가능
  - 최대 16개 EC2까지
  - 모두 같은 AZ에 있어야 함
  - 여러 EC2가 읽기/쓰기를 모두 할 수 있음
- 인스턴스 종료 시 루트 EBS는 삭제, 추가 EBS는 유지가 기본 동작 (Delete on Termination 속성).

**Delete on Termination 속성:**

| 볼륨 유형 | 기본값            | 설명                             |
| --------- | ----------------- | -------------------------------- |
| 루트 EBS  | 삭제 O (활성화)   | 인스턴스 종료 시 함께 삭제       |
| 추가 EBS  | 삭제 X (비활성화) | 인스턴스 종료 후에도 데이터 유지 |

> 💡 **시험 포인트**:
>
> - EBS는 특정 가용영역에 고정되어있어 **AZ에 종속** (Cross-AZ 직접 연결 불가)
> - 루트 볼륨의 Delete on Termination은 **기본값 활성화**, 비루트는 **기본값 비활성화**
> - 인스턴스 종료 후 루트 볼륨 데이터를 보존하려면 Delete on Termination을 **비활성화**

## 2. EBS Snapshots

**EBS 스냅샷**은 EBS 볼륨의 특정 시점 백업이다. 스냅샷을 생성하기 위해 EBS를 분리할 필요는 없지만, 권장된다.

**활용:**

- 스냅샷을 다른 AZ나 리전에 복사 → Cross-AZ/Cross-Region 볼륨 이동 가능

### 스냅샷 주요 기능 3가지

| 기능                            | 설명                                     | 비용/특이사항                   |
| ------------------------------- | ---------------------------------------- | ------------------------------- |
| **EBS Snapshot Archive**        | 스냅샷을 Archive 계층으로 이동           | 75% 저렴, 복원에 24~72시간 소요 |
| **Recycle Bin**                 | 삭제된 스냅샷을 복원 가능하도록 보관     | 보관 기간 1일~1년 설정          |
| **Fast Snapshot Restore (FSR)** | 스냅샷에서 볼륨 생성 시 초기화 지연 없음 | 비용 높음                       |

> 💡 **시험 포인트**:
>
> - EBS 스냅샷으로 **다른 AZ/리전으로 데이터 이동** 가능
> - Archive 스냅샷은 복원에 **최대 72시간** 소요
> - FSR은 대용량 볼륨에서 첫 읽기 지연 없애지만 **비용이 높다**

## 3. AMI (Amazon Machine Image)

**AMI**는 EC2 인스턴스의 커스터마이즈 템플릿이다. OS, 소프트웨어, 설정, 모니터링 도구 등을 사전 패키징하여 빠른 부팅과 구성이 가능하다.

**AMI는 특정 리전에 종속**되며, 다른 리전으로 복사해 사용할 수 있다.

### AMI 유형

| 유형                    | 설명                                         |
| ----------------------- | -------------------------------------------- |
| **Public AMI**          | AWS가 제공하는 공식 AMI (예: Amazon Linux 2) |
| **Own AMI**             | 직접 만들고 관리하는 AMI                     |
| **AWS Marketplace AMI** | 서드파티 업체가 만들어 판매하는 AMI          |

### AMI 생성 프로세스

```
① EC2 인스턴스 시작
② 인스턴스 커스터마이즈 (패키지 설치, 설정 등)
③ 인스턴스 중지 (데이터 무결성 보장)
④ AMI 빌드 → EBS 스냅샷 자동 생성
⑤ 생성된 AMI로 다른 AZ/리전에서 인스턴스 시작
```

> 💡 **시험 포인트**:
>
> - AMI는 **리전 종속** → 다른 리전 사용 시 복사 필요
> - AMI 빌드 시 내부적으로 **EBS 스냅샷**이 생성됨
> - Marketplace AMI는 추가 비용 발생 가능

## 4. EC2 Instance Store

**EC2 Instance Store**는 EC2 인스턴스에 직접 물리적으로 연결된 임시 디스크다.  
EBS보다 훨씬 높은 I/O 성능을 제공한다.

**주요 특징:**

- 매우 높은 IOPS 제공 (예: I3 인스턴스 3.3 million read IOPS)
- **임시(Ephemeral) 스토리지** → 인스턴스 중지 또는 종료 시 데이터 손실  
  = 장기적으로 데이터를 보관할만한 장소가 될 수 없음
- 하드웨어 장애 발생 시 데이터 손실 위험
- 버퍼, 캐시, 스크래치 데이터, 임시 콘텐츠에 적합

**용도:** 고성능 I/O가 필요한 버퍼/캐시/스크래치 데이터. 장기 저장은 EBS나 S3 사용.

> 💡 **시험 포인트**:
>
> - Instance Store = **물리적 연결** → 매우 높은 I/O 성능
> - **인스턴스 중지/종료 시 데이터 손실** (비영구적)
> - 장기 보존이 필요한 데이터는 EBS나 S3 사용

## 5. EBS Volume Types

EBS는 6가지 볼륨 유형을 제공한다.

### 5-1. General Purpose SSD (범용 SSD)

| 항목        | gp3                   | gp2                   |
| ----------- | --------------------- | --------------------- |
| 크기        | 1 GiB ~ 16 TiB        | 1 GiB ~ 16 TiB        |
| 기본 IOPS   | 3,000                 | 3 IOPS/GiB (최소 100) |
| 최대 IOPS   | 16,000                | 16,000                |
| 기본 처리량 | 125 MiB/s             | -                     |
| 최대 처리량 | 1,000 MiB/s           | -                     |
| 특징        | IOPS/처리량 독립 설정 | 크기와 IOPS 연동      |

- 부팅 볼륨, 개발/테스트 환경, 가상 데스크탑에 적합

### 5-2. Provisioned IOPS SSD (프로비저닝 IOPS SSD)

| 항목      | io1                | io2 Block Express            |
| --------- | ------------------ | ---------------------------- |
| 크기      | 4 GiB ~ 16 TiB     | 4 GiB ~ 64 TiB               |
| 최대 IOPS | 64,000 (Nitro EC2) | 256,000                      |
| 지연시간  | -                  | 서브 밀리초                  |
| 특징      | 고성능 DB 워크로드 | 최고 성능, Multi-Attach 지원 |

- **지속적인 고성능 IOPS**가 필요한 DB 워크로드에 적합
- io1/io2만 **Multi-Attach** 지원

### 5-3. HDD (하드 디스크 드라이브)

| 항목        | st1 (Throughput Optimized)        | sc1 (Cold HDD)            |
| ----------- | --------------------------------- | ------------------------- |
| 크기        | 125 GiB ~ 16 TiB                  | 125 GiB ~ 16 TiB          |
| 최대 처리량 | 500 MiB/s                         | 250 MiB/s                 |
| 최대 IOPS   | 500                               | 250                       |
| 용도        | Big Data, 로그, 데이터 웨어하우스 | 자주 접근하지 않는 데이터 |ㅇㄹ
| 비용        | -                                 | 가장 저렴                 |

### 부팅 볼륨 가능 여부

| 유형      | 부팅 볼륨 |
| --------- | --------- |
| gp2 / gp3 | ✅ 가능   |
| io1 / io2 | ✅ 가능   |
| st1 / sc1 | ❌ 불가   |

> 💡 **시험 포인트**:
>
> - **HDD(st1/sc1)는 부팅 볼륨으로 사용 불가**
> - gp3는 gp2와 달리 **IOPS와 처리량을 독립적으로 설정** 가능
> - 64,000 IOPS 이상이 필요하면 **io2 Block Express** (최대 256,000 PIOPS)
> - 최고 처리량이 필요한 순차 작업(Big Data) → **st1**

## 6. EBS Multi-Attach

**io1/io2 볼륨만** Multi-Attach를 지원한다. 하나의 EBS 볼륨을 **동일 AZ** 내의 최대 **16개** EC2 인스턴스에 동시 연결 가능하다.

**요구사항:**

- 클러스터 인식 파일 시스템(Cluster-Aware Filesystem) 필수
- XFS, EXT4 같은 일반 파일 시스템은 사용 불가

**활용:** 동시 쓰기 작업이 필요한 고가용성 클러스터 애플리케이션

> 💡 **시험 포인트**:
>
> - Multi-Attach는 **io1/io2만** 지원
> - **같은 AZ** 내에서만 동작
> - 최대 **16개** EC2 인스턴스에 동시 연결
> - XFS, EXT4 등 일반 파일 시스템 **사용 불가** (클러스터 인식 FS 필요)

## 7. EBS Encryption

EBS 볼륨을 암호화하면 다음이 모두 암호화된다:

- 볼륨의 저장 데이터 (data at rest)
- 인스턴스와 볼륨 간의 전송 중 데이터
- 스냅샷
- 스냅샷으로 생성한 볼륨

**특징:**

- KMS(AES-256) 사용
- EC2와 EBS 사이에서 투명하게 처리됨 (애플리케이션 코드 변경 없음)
- 성능 영향 최소화

### 암호화되지 않은 EBS 볼륨을 암호화하는 방법

```
① 기존 비암호화 EBS 볼륨의 스냅샷 생성
② 스냅샷 복사 시 암호화 옵션 활성화
③ 암호화된 스냅샷으로 새 EBS 볼륨 생성
④ 새 암호화된 볼륨을 인스턴스에 연결
```

> 💡 **시험 포인트**:
>
> - 암호화된 볼륨의 스냅샷은 **자동으로 암호화**됨
> - 비암호화 볼륨을 암호화하려면 **스냅샷 복사 → 암호화 적용** 경로 사용
> - KMS AES-256 사용, 지연시간 영향 최소

## 8. Amazon EFS

**EFS(Elastic File System)**는 여러 EC2 인스턴스에서 동시에 마운트할 수 있는 관리형 NFS(Network File System)다.

**주요 특징:**

- NFSv4.1 프로토콜 사용
- 여러 AZ에 걸쳐 EC2 인스턴스가 공유 가능 (Multi-AZ)
- **Linux만 지원** (POSIX 파일 시스템, Windows 미지원)
- 자동 확장 (사전 용량 설정 불필요)
- 사용한 만큼 비용 지불 (pay-per-use)
- gp2 EBS보다 약 **3배 비싸지만** 스토리지 클래스로 비용 절감 가능

### 성능 모드 (Performance Mode)

| 모드                         | 특징                            | 용도                               |
| ---------------------------- | ------------------------------- | ---------------------------------- |
| **General Purpose** (기본값) | 낮은 지연시간                   | 웹 서버, CMS, 지연시간에 민감한 앱 |
| **Max I/O**                  | 높은 처리량, 약간 높은 지연시간 | 빅데이터, 미디어 처리              |

### 처리량 모드 (Throughput Mode)

| 모드            | 특징                                                             |
| --------------- | ---------------------------------------------------------------- |
| **Bursting**    | 1 TB = 50 MiB/s 기본 + 최대 100 MiB/s 버스트                     |
| **Provisioned** | 스토리지 크기와 무관하게 처리량 독립 설정                        |
| **Elastic**     | 워크로드에 따라 자동 확장/축소 (최대 3 GiB/s 읽기, 1 GiB/s 쓰기) |

### 스토리지 클래스

| 클래스                         | 설명                               | 비용                |
| ------------------------------ | ---------------------------------- | ------------------- |
| **Standard**                   | 자주 접근하는 파일                 | 기본 비용           |
| **EFS-IA (Infrequent Access)** | 자주 접근하지 않는 파일            | 저렴                |
| **Archive**                    | 거의 접근하지 않는 파일 (연 몇 회) | EFS-IA보다 50% 저렴 |

- 수명 주기 정책(Lifecycle Policy)으로 파일을 자동으로 계층 간 이동

### 가용성

| 옵션                    | 특징                       | 용도                               |
| ----------------------- | -------------------------- | ---------------------------------- |
| **Standard (Multi-AZ)** | 여러 AZ에 걸쳐 데이터 복제 | 프로덕션                           |
| **One Zone**            | 단일 AZ, 기본 백업 활성화  | 개발/비용 절감 (Standard보다 저렴) |

> 💡 **시험 포인트**:
>
> - EFS는 **Linux 전용** (POSIX 파일 시스템), Windows 미지원
> - 여러 AZ의 여러 인스턴스가 **동시에 마운트** 가능
> - 스토리지 클래스: Standard → EFS-IA → Archive (접근 빈도 낮을수록 저렴)
> - One Zone은 Standard보다 약 **90% 저렴**하지만 단일 AZ 장애에 취약

## 9. EBS vs EFS 비교

| 항목             | EBS                       | EFS                    |
| ---------------- | ------------------------- | ---------------------- |
| 연결 인스턴스 수 | 1개 (io1/io2는 최대 16개) | 수백 개 동시 마운트    |
| AZ 범위          | AZ에 종속                 | Multi-AZ               |
| 운영체제         | Linux, Windows            | **Linux 전용**         |
| 파일 시스템      | 블록 스토리지             | NFS (공유 파일 시스템) |
| 비용             | 프로비저닝 용량           | 사용량 기준            |
| 이동 방법        | 스냅샷 → 다른 AZ에서 복원 | 기본적으로 Multi-AZ    |

**EBS 요약:**

- 하나의 인스턴스에 연결된 단독 고성능 블록 스토리지
- AZ 간 이동 시 스냅샷 필요
- EC2 종료 시 루트 볼륨은 기본 삭제

**EFS 요약:**

- 수백 개 인스턴스가 동시 공유
- Multi-AZ 기본 지원 (One Zone 옵션도 존재)
- Linux 전용, 비용은 EBS보다 높지만 공유 특성으로 효율적

> 💡 **시험 포인트**:
>
> - "여러 인스턴스/AZ에서 파일 공유" → **EFS**
> - "단일 인스턴스, 고성능 블록 스토리지" → **EBS**
> - EFS는 **Linux Only**, EBS는 Linux/Windows 모두 지원
